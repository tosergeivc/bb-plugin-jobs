# bb-plugin-jobs

English version: [README.md](README.md).

Плагин bb: команда `bb jobs` запускает долгие команды (серверы, деплои, сборки) как фоновые задачи, которые не умирают вместе с ходом агента, ждёт готовности сервера и сообщает треду агента о завершении задачи.

## Зачем

Процессы, запущенные агентом через Bash, живут в дереве процессов bb. Провайдер агента завершает дерево своих процессов в конце хода (проверено: `nohup … &` и `setsid` не пережили конец хода). На Linux bb часто работает как `bb-app.service` с `KillMode=control-group`, и остановка или обновление сервиса убивает все процессы его cgroup.

## Как работает

- `server.ts` регистрирует CLI `bb jobs`. Команда выполняется на сервере bb и пересылает вызов host-entry на машину треда (thread → environment → hostId) или на `--machine`.
- `host.ts` работает в демоне bb на этой машине и вызывает `JobManager` из `jobs-core.ts`.
- Linux с user systemd: задача — transient unit `bbjob-<id>` (`systemd-run --user --collect`), своя cgroup вне `bb-app.service`. Остановка — `systemctl --user stop`, убивает всё дерево.
- Без user systemd (macOS): detached-процесс (новая сессия). Сохранённому PID плагин не доверяет: PID выдаются повторно. Процесс принадлежит задаче, если его командная строка точно совпадает с запуском файлов задачи (`runner.sh`, `exec.pl`, `command.sh`), если он их потомок, или если он в группе процессов команды, запущен не раньше задачи, а лидер группы — процесс задачи или уже завершился. Чужой процесс с тем же PID или `tail -f …/output.log` не считается задачей и не получает сигнал. Метку в окружении использовать нельзя: macOS скрывает окружение чужих процессов. Остановка — SIGTERM, через 10 с SIGKILL.
- `runner.sh` (своя копия в каталоге каждой задачи, не перезаписывается во время работы) переходит в каталог и передаёт управление `exec.pl`. Тот запускает команду в отдельной группе процессов, пишет вывод в `output.log` с ограничением размера, следит за `--timeout` и сразу после завершения команды записывает код выхода в файл `exit`. Задача не зависит от воркера bb.

## Команды

| Команда | Что делает |
|---------|------------|
| `bb jobs start --name <метка> -- <команда>` | Запуск в текущем каталоге; `--cwd`, `--env K=V`, `--timeout 30m`, `--log-max 50` (МиБ) |
| `bb jobs start … --ready-url URL` или `--ready-log REGEX` [`--ready-timeout 60s`] | Запуск и ожидание готовности: URL ответил 2xx или в логе появилась строка. Код 0 — готово, 1 — задача завершилась, 124 — ещё не готово (задача продолжает работать) |
| `bb jobs start … --notify` или `--notify-thread THREAD` | Когда задача завершится, отправить в вызвавший (или указанный) тред результат, команду, время и последние 2 КиБ вывода |
| `bb jobs ready <id> --url URL` или `--log REGEX` | Та же проверка готовности для уже запущенной задачи |
| `bb jobs list [--running] [--all]` | Задачи вызвавшего треда, новые первыми; `--all` — задачи всех тредов машины |
| `bb jobs status <id>` | Состояние, код выхода, путь к логу |
| `bb jobs logs <id> [--bytes N] [--raw]` | Конец лога без цветовых кодов и перерисовок прогресс-баров (`--raw` оставляет их) |
| `bb jobs logs <id> --since N` | Только вывод после курсора N, целыми строками; каждый вызов печатает `next: --since N` |
| `bb jobs wait <id> [--timeout 5m]` | Ждать завершения (до 10 мин за вызов) |
| `bb jobs stop <id> [--force]` | Остановить всё дерево процессов; работающую задачу другого треда — только с `--force` |
| `bb jobs prune --older-than 7d [--delete] [--dry-run] [--all]` | Перенести завершённые задачи старше срока в `archive/` плагина или удалить (`--delete`); работающие задачи не трогает. Из треда — только задачи этого треда (как `list`), `--all` — все задачи машины; вне треда — все |

Состояния: `running`, `exited`, `stopped`, `lost` (исчезла без кода выхода), `incomplete` (запуск прервался между стартом и подтверждением; сейчас ничего не работает, но неизвестно, выполнялась ли команда: смотрите лог и на Linux `systemctl --user status bbjob-<id>`), `not-started` (запуск сорвался до появления процесса; в `list` не показывается).

Код ошибки запуска: `start_refused` — ничего не запускалось (нет каталога или env-файла, неверное значение, `systemd-run` отверг юнит); `start_unknown` — ответ потерян (например, таймаут), задача может работать. Такой запуск повторяйте с тем же `--key` или сначала проверьте `bb jobs list`.

## Ограничения

- `bb jobs` управляет жизнью команды (запуск, вывод, код выхода, остановка), но это не система развёртывания: он не утверждает выпуски, не принимает артефакты и не откатывает. Код 0, готовность или уведомление значат «команда завершилась», а не «развёртывание верно».
- Задача `ssh host команда` — это локальный клиент `ssh`. `stop` и `--timeout` завершают клиента; без терминала (`ssh -tt`) удалённая команда может продолжить работу. Если машина подключена к bb — запускать на ней отдельную задачу через `--machine`.
- `--key` действует в пределах машины и привязан к запросу (команда, каталог, хеши `--env`, путь env-файла, `--timeout`, лимиты, `--require-systemd`; `--name`, `--log-max` и содержимое env-файла не входят): другой запрос с занятым ключом — ошибка `key_conflict`. У ключа есть история захватов; каждую следующую запись может добавить только один процесс, поэтому одновременные запуски даже из разных процессов дают одну задачу. Захват хранит процесс и время его старта, поэтому чужой процесс с тем же PID ключ не держит. Ключ ничем не освобождается по времени: запуск, ещё идущий в другом процессе, даёт `key_busy`, оборвавшийся на полпути — `key_unknown`; освободить после проверки — `bb jobs release-key <ключ>`. Без `--force` `release-key` отказывает, пока идёт запуск с этим ключом или существует запущенная им задача (при `key_busy` дождитесь и повторите запуск). Ничего не удаляется: старый захват остаётся в истории, каталоги задач отвязываются от ключа.
- Ключи 0.5.3 не видны версиям 0.5.0–0.5.2: не откатывайтесь, пока запуски с ключами могут повторяться.
- После `prune` задачи ключ свободен, даже если команда оставила процесс вне задачи (`setsid`, `nohup … &`, запущенный ею сервис): следующий запуск с этим ключом выполнит команду снова. Не делайте prune для ключевых задач развёртывания, пока такие процессы могут работать.

- Ограничение лога и `--timeout` работают через perl (есть в macOS и Ubuntu). Без perl задача с `--timeout` завершается с кодом 125, остальные задачи пишут лог без ограничения.
- Лог хранит не больше двух `--log-max` (по умолчанию 50 МиБ): при превышении `output.log` становится `output.log.1`. `bb jobs logs` читает оба файла.
- В режиме detached дочерний процесс, который создал свою сессию или группу (`setsid`, многие демоны), находится, пока жив его родитель из задачи, но не после его завершения.
- Режим `detached` на Linux переживает конец хода, но не полную остановку `bb-app.service`.
- Задача наследует только PATH, HOME, USER, LOGNAME, SHELL, LANG, LC_ALL, TZ, SSH_AUTH_SOCK; остальное — через `--env`. При запуске из треда она также получает `BB_THREAD_ID` и `BB_PROJECT_ID`, а на машине треда ещё `BB_ENVIRONMENT_ID` и `BB_THREAD_STORAGE`.
- `--notify`: служба на сервере bb каждые 5 с проверяет отмеченные задачи и отправляет в тред одно сообщение (`queue-if-active`): активный тред получит его после текущего хода, неактивный начнёт новый ход. Доставка «хотя бы раз»: при остановке сервера в неудачный момент сообщение может прийти дважды. Задачи, остановленные через `bb jobs stop`, и удалённые треды не уведомляются.
- Linux: чтобы задачи жили после выхода пользователя из системы, нужен linger: `sudo loginctl enable-linger $USER`. `bb jobs start` предупреждает, если он выключен.
- Windows-машины не поддерживаются: `bb jobs start` отказывает с понятной ошибкой. WSL работает.
- Значения `--env` ненадолго пишутся на диск: в `env.sh` (права 0600), задача читает и удаляет этот файл до запуска команды; если задача не стартовала, файл удаляет runner или следующий `status`/`list`. Значения остаются в окружении процесса задачи и проходят через командную строку `bb`, поэтому их видит другой процесс того же пользователя в аргументах `bb`. Для секретов использовать `--env-file <абсолютный путь>`: значения остаются в файле на машине задачи (права ровно 600, иначе `start` откажет) и читаются только задачей. Саму команду не использовать для секретов: она хранится в `meta.json` и видна в `bb jobs status`.
- Каталоги завершённых задач не удаляются автоматически: для этого `bb jobs prune`. По умолчанию prune переносит их в `archive/`, место на диске при этом не освобождается; освобождает `--delete`.

## Хорошо сочетается с

- [Lame duck](https://github.com/ymichael/bb-plugins) — приостанавливает новые сообщения и даёт активным ходам завершиться перед перезапуском или обновлением сервера bb. Список `--notify` хранится на сервере, поэтому уведомления о задачах, завершившихся во время перезапуска, придут после него.
- [Env Catalog](https://github.com/VKirill/bb-plugin-env-catalog) — зашифрованное хранилище секретов на сервере bb. Секрет передавать как `--env NAME="$NAME"`, а не писать в команду.
- `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` — настройка, которая есть в Claude Code 2.1.310. По [README Shell tasks](https://github.com/ahkohd/bb-plugin-shell-tasks#install) она отключает фоновые Bash-команды Claude Code (их процессы тоже гибнут с концом сессии), и агент использует `bb jobs`. Включение: `printf '1\n' | bb machine env set CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`. Здесь её действие не проверялось.

## Похожие плагины

В маркетплейсе bb-community на 24.10.2026 есть [Terminal Jobs](https://github.com/ryanbbrown/bb-plugin-terminal-jobs) и [Shell tasks](https://github.com/ahkohd/bb-plugin-shell-tasks). Оба запускают команду из демона bb (`spawn` с `detached: true`), поэтому на Linux процесс остаётся в cgroup сервиса bb и завершается при его остановке или обновлении. `bb jobs` запускает задачу отдельным unit `systemd-run --user`, умеет ждать готовности, ограничивает лог и защищает от повторно выданных PID. У них есть то, чего нет у нас: панель в интерфейсе (Shell tasks), записи в SQLite с повтором уведомления (Terminal Jobs). Не ставьте несколько таких плагинов сразу: их навыки для агентов спорят.

## История версий

- **0.5.4** — `bb jobs prune` из треда переносит или удаляет только задачи этого треда, как `list`; `--all` — задачи всех тредов машины. Раньше prune из одного треда убирал в архив и завершённые задачи других тредов.
- **0.5.3** — `--key` держится между процессами: захваты стали нумерованной историей, каждую запись которой может добавить только один процесс, поэтому два процесса с одним ключом запускают одну задачу (раньше гонка запускала две-три). Захват хранит время старта процесса: повторно занятый PID больше не держит ключ. Повреждённый захват даёт `key_unknown`, и `release-key` его освобождает. Прерванный после старта запуск виден в `list` как `incomplete` и останавливается; запуск, сорвавшийся до появления процесса (`systemd-run` отверг юнит), сразу освобождает ключ вместо `key_unknown`. `release-key` отказывает без `--force`, пока идёт запуск с ключом или существует запущенная им задача, и отвязывает ключ от всех каталогов. Ошибка после старта оставляет ключ привязанным: повтор с тем же ключом вернёт задачу. `/tmp/` и `/tmp` — один каталог; ключ из 0.5.0/0.5.1 сверяется по команде и каталогу. Ошибки запуска: `start_refused` (ничего не запускалось) и `start_unknown` (ответ потерян, задача может работать). Отказ для `--cpu-quota 0%`, `--memory-max 0` и процентов больше 100. Тесты: три процесса одновременно с одним ключом.
- **0.5.2** — `--key` больше не освобождает захват через 15–60 секунд (это могло запустить вторую задачу при медленном первом запуске): запуски с одним ключом ждут друг друга, чужой живой захват даёт `key_busy`, мёртвый владелец проверяется по каталогу задачи (`key_unknown`, если запуск оборвался на полпути), `bb jobs release-key` освобождает ключ переименованием; ключ привязан к запросу (`key_conflict`). `--env-file` с правами шире 600 — отказ. Навык больше не советует `--env TOKEN="$TOKEN"`.
- **0.5.1** — неверные значения `--memory-max`, `--cpu-quota`, `--key`, `--env-file` и отказ машины (нет каталога, env-файла или systemd для лимитов) приходят как ошибки ввода с подсказкой; раньше `bb plugin list` показывал их как «cli jobs failed» рядом с работающим плагином.
- **0.5.0** — `--key` (идемпотентный запуск: повтор и одновременные запуски с одним ключом дают одну задачу); `--env-file` (секреты из файла на машине задачи, мимо bb); `--memory-max`, `--cpu-quota`, `--tasks-max` (лимиты systemd); `--require-systemd` (отказ вместо detached); README: `env.sh` пишется ненадолго, ssh-задачи, «не система развёртывания».
- **0.4.3** — работает с SDK плагинов bb 0.6.43 и новее (bb 0.46.1); если bb не может поставить уведомление в очередь занятого треда, оно ждёт, пока тред освободится, и уходит напрямую; неудачные отправки повторяются с растущей паузой до 72 часов, а не отбрасываются после пяти попыток.
- **0.4.2** — строка `[jobs] exited` пишется после всего вывода команды (раньше могла оказаться перед последними строками, а после ротации — в `output.log.1`); процессы задачи распознаются при любом пути или версии интерпретатора bash/perl в `ps`; CI на Linux и macOS.
- **0.4.1** — короткие уведомления (строка результата с длительностью, где лог, 5 последних строк при коде 0, иначе 2 КиБ, без повторных строк `[jobs]`); по умолчанию уведомления видит только агент (настройка `notifyVisibility`; `bb plugin config jobs set notifyVisibility visible` — показывать и в чате; проверено на Claude Code и Codex); записи об отправленных уведомлениях чистятся раз в минуту. Отозвать уведомление можно, только пока оно ждёт в очереди занятого треда; в свободный тред оно уходит сразу и запускает ход.
- **0.4.0** — `logs` без цветовых кодов (`--raw` — с ними) и чтение порциями (`--since`); `--ready-log` ищет по очищенному тексту; одно уведомление на несколько задач треда, уведомление отменяется, если агент уже прочитал результат; `list` по умолчанию показывает задачи своего треда (`--all` — все); `stop` чужой задачи — только с `--force`; в навыке — `bb connect expose` для удалённого просмотра.
- **0.3.0** — `--notify` и `--notify-thread`; переменные `BB_*` в задаче; предупреждение о выключенном linger; отказ на Windows; служебные строки `[jobs]` всегда с новой строки; тесты переносимы на macOS; `PLUGIN_OVERVIEW.md`. Короткое описание больше не обещает переживать перезапуск bb: это не проверено.

- **0.2.0** — ожидание готовности (`--ready-url`, `--ready-log`, `bb jobs ready`); ограничение и ротация лога (`--log-max`); `bb jobs prune`; detached-задачи узнаются по командной строке запуска и группе процессов, чужой процесс с тем же PID не трогается; своя копия runner для каждой задачи; код выхода записывается, даже если оставшийся дочерний процесс держит вывод.
- **0.1.1** — значения `--env` не хранятся на диске.
- **0.1.0** — первая версия.
